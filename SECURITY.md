# Security Policy

## Supported Versions

Security updates are provided for actively maintained versions of the project.

| Version | Supported |
| ------- | --------- |
| Latest release | :white_check_mark: |
| Older releases | :x: |

Users are encouraged to keep their installations updated to the latest available version.

## Reporting a Vulnerability

If you discover a security vulnerability, please **do not report it through a public GitHub issue**.

Instead, report it privately to:

**miguelobx34@gmail.com**

Please include as much information as possible to help us understand and reproduce the issue, including:

- A description of the vulnerability.
- The affected version or versions.
- Steps required to reproduce the vulnerability.
- The potential impact.
- Any proof of concept, logs, screenshots, or relevant code.
- Any suggested mitigation or fix, if available.

Please do not include passwords, API keys, access tokens, personal information, or other sensitive credentials unless they are strictly necessary to demonstrate the vulnerability.

## What to Expect

We will acknowledge receipt of a vulnerability report as soon as reasonably possible.

After receiving a report, we will:

1. Review and investigate the reported vulnerability.
2. Determine whether the issue affects a supported version.
3. Assess the severity and potential impact.
4. Work on a fix or mitigation when appropriate.
5. Release a security update when necessary.
6. Notify the reporter when the issue has been addressed.

We ask that reporters allow reasonable time for investigation and remediation before publicly disclosing the vulnerability.

## Security Updates

Security fixes may be released as:

- A new patch release.
- A new minor or major release when required.
- A security advisory.
- An update to the project's documentation or configuration.

Users should regularly update to the latest supported version to receive security fixes.

## Vulnerability Disclosure

Please do not publicly disclose the vulnerability until the maintainers have had a reasonable opportunity to investigate and address it.

Once the issue has been resolved, the maintainers may publish information about the vulnerability, including its impact and the affected versions.

Sensitive information that could put users or systems at risk will not be disclosed.

## Scope

Security reports should concern vulnerabilities that affect the security, integrity, confidentiality, or availability of the project or its users.

Examples include:

- Authentication or authorization vulnerabilities.
- Sensitive information disclosure.
- Remote code execution.
- Privilege escalation.
- Injection vulnerabilities.
- Improper handling of credentials or secrets.
- Security-related configuration issues.
- Other vulnerabilities that could reasonably compromise the project or its users.

## Out of Scope

The following are generally not considered security vulnerabilities unless they have a significant security impact:

- Issues affecting unsupported versions.
- Problems caused by outdated third-party dependencies when no vulnerability is introduced by this project.
- General bugs without a security impact.
- Feature requests.
- Denial-of-service reports against third-party infrastructure.
- Social engineering or phishing attempts against project contributors.

If you are unsure whether an issue is security-related, please report it privately anyway.

## Responsible Disclosure

We appreciate responsible disclosure and will make a reasonable effort to work with security researchers and contributors to understand and resolve reported vulnerabilities.

Thank you for helping us keep the project and its users secure.
